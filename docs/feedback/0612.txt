
HearHere 页面优化 - Claude 可操作指令模板

模块一：多人冲突协调逻辑
[修改模块]：多人冲突协调（原 /harmony 页面逻辑）
[修改目标]：删除多人冲突界面，改为后台自动分析整合用户需求生成最适合的攻略。
[修改要求]：
1. 不再为用户展示冲突协调页面。
2. 后台接收到多人需求后，自动分析：
   - 时间冲突
   - 偏好冲突
   - 硬性约束
3. 将分析结果整合入最终攻略生成逻辑中。
4. 输出的攻略中，体现对不同用户需求的平衡和优先级，而无需用户干预。
5. 移除原先页面 UI/交互逻辑相关文件和路由。
[示例输入]：
三人出行：
- A：预算1000元，偏好海鲜
- B：预算1500元，偏好素食
- C：预算1200元，偏好海鲜/景点
[验证方法]：
1. 输入多人需求，生成攻略。
2. 验证攻略中是否综合考虑所有人的约束和偏好。
3. 确认删除多人冲突页面 UI，不再可访问。

模块二：美食灵感页面
[修改模块]：美食灵感页面（/explore/food 或独立美食列表页）
[修改目标]：确保页面只展示美食相关内容，剔除非美食信息。
[修改要求]：
1. 页面仅展示美食类型、特色菜或菜系。
2. 移除非美食内容，例如纪念品、伴手礼、景点。
3. 如果用户搜索地名，如徐州，则屏蔽“徐州香包”等非美食内容。
4. 保持 UI 风格一致，确保与景点卡片页面区分。
5. 推荐理由可简短突出特色，但无需生成无效信息。
[示例输入]：
用户搜索：徐州旅行
[验证方法]：
1. 在美食页面输入不同地名测试。
2. 确认页面不出现任何非美食内容。
3. 美食推荐理由清晰、与用户旅行需求相关。

模块三：景点与美食卡片推荐
[修改模块]：景点卡片 / 美食卡片推荐模块
[修改目标]：增加卡片数量与多样性，提高推荐理由的针对性与吸引力。
[修改要求]：
1. 增加推荐卡片数量，覆盖主要景点与美食。
2. 景点卡片推荐理由必须：
   - 根据用户实际出行需求因地制宜
   - 说明景点特殊性、时间安排或交通信息
   - 标识郊区景点，提示用户需要预留出行时间
3. 美食卡片独立展示，突出特色菜、菜系，不与景点卡片混合
4. 避免笼统模板描述，如“适合全家放松”“宗教文化体验”
5. 推荐理由根据用户选择卡片、出行时间、同行人员偏好生成
[示例输入]：
目的地：普陀山
用户选择景点卡片：
- 海边
- 普济寺
- 南海观音
[期望输出]：
- 海边卡片：
  - 描述：傍晚观赏日落，适合拍照，离市区约20分钟车程
- 普济寺卡片：
  - 描述：普陀山三大古寺之一，适合带父母慢游
- 南海观音卡片：
  - 描述：上午游客较少，可避开人流，享受祈福体验
美食卡片：
- 海鲜、素斋、梭子蟹
- 每条理由突出地方特色，不包含餐厅名称
[验证方法]：
1. 检查每个推荐卡片是否真实、可搜索
2. 景点理由与用户需求匹配，因地制宜
3. 郊区景点明确标识距离及时间安排
4. 美食卡片独立于景点卡片，且只展示美食信息
