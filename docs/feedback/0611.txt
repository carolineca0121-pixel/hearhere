HearHere 产品深度优化修改需求
请基于当前 HearHere 项目代码进行完整检查和修改。
这次不是简单 UI 调整，而是需要从产品体验和核心逻辑层面优化。请先理解当前完整用户流程：
语音输入 → 需求提取 → 标签确认 → 卡片选择 → 生成定制攻略 → 行程查看 → 用户继续调整
目标：让最终生成的攻略真正达到「用户可以直接照着执行」的程度，而不是泛泛的旅行信息总结。

一、优化生成过程体验
1. 推荐卡片加载体验优化
当前问题：
进入探索卡片页面后，卡片出现速度较慢，用户会感觉页面没有反馈，不知道系统是否正在工作。
优化目标：
不要让用户等待一个黑盒结果。
需要增加生成过程中的视觉反馈。
建议：
在语音输入结束后，到卡片展示之间增加一个中间状态：
例如：
「正在理解你的旅行偏好」 ↓ 「正在帮你匹配适合你的目的地体验」 ↓ 「为你生成专属推荐」
可以使用：
	•	呼吸动画
	•	骨架屏
	•	渐进式卡片加载
	•	AI 思考状态
让用户知道： 系统正在根据刚才的需求生成，而不是卡顿。

2. 行程生成等待优化
当前问题：
点击生成攻略后等待时间过长，用户容易失去耐心。
要求：
增加生成过程状态。
例如：
不要显示：
“生成中……”
而是：
“正在整理你的旅行节奏” “正在安排景点顺序” “正在匹配适合你的餐厅” “正在生成你的专属攻略”
同时检查：
	•	是否可以提前返回部分内容
	•	是否可以流式生成
	•	是否可以降低首次等待时间

二、攻略生成核心逻辑优化
1. 攻略标题生成
当前问题：
标题直接复制用户语音：
例如：
“探索我和爸妈计划后天从上海自驾去普陀山玩三天”
这是错误的。
要求：
生成一个产品化标题。
根据：
	•	出行人物
	•	目的地
	•	时间
	•	旅行方式
	•	核心偏好
自动总结。
例如：
输入：
“我和爸妈后天上海自驾去普陀山玩三天”
输出：
「轻松家庭普陀山三日慢旅行」
或者：
「陪爸妈的普陀山祈福休闲之旅」
不要直接展示用户原话。

2. 删除“情感高光时刻”模块
当前问题：
情感高光时刻为空，没有图片。
要求：
直接移除该模块。
不要展示空内容。

3. 旅途歌单重新设计
当前问题：
现在推荐：
朴树、陈绮贞、孙燕姿
太大众化。
和 HearHere 的“定制化旅行助手”定位冲突。
要求：
歌单必须基于用户画像。
例如：
用户： “陪父母去普陀山”
推荐方向：
	•	父母熟悉年代歌曲
	•	安静旅途音乐
	•	适合自驾氛围
而不是随机热门歌手。
同时：
目前写：
“旅途歌单仅视觉参考”
但页面没有任何视觉参考。
二选一：
方案 A： 增加视觉化展示：
	•	音乐卡片
	•	氛围标签
	•	场景描述
例如：
「清晨自驾｜温柔怀旧」
方案 B：
如果没有真实音乐能力，删除歌单模块。
不要保留无价值模块。

三、攻略内容生成逻辑重构（重点）
当前最大问题：
生成内容像模板，而不是定制攻略。
必须改变。
核心原则：
用户选择的卡片 = 用户真实意愿。
攻略必须围绕用户选择内容展开。

时间节点优化
当前：
9:00 探索目的地
这种描述没有意义。
要求：
每个时间点必须包含：
	1	具体地点
	2	为什么安排这个时间
	3	体验目的
	4	交通/时间合理性
例如：
错误：
9:00 探索目的地
正确：
9:00 上海自驾前往普陀山
预计车程约 X 小时
建议上午抵达后先休息，再前往普济寺。
原因：
上午游客较少，更适合陪父母慢慢游览。

四、景点卡片必须进入攻略
当前问题：
用户选择了卡片，但攻略没有体现。
例如：
用户选择：
海边
寺庙
特色街区
结果：
生成：
“感受当地烟火气”
这是无效内容。
要求：
所有用户右滑选择的卡片：
必须进入最终攻略。
规则：
卡片 → 行程节点
例如：
选择： 普济寺
生成：
14:30 普济寺参拜
原因：
下午游客相对减少，适合慢节奏游览。
选择： 海边
生成：
17:00 海边看日落
原因：
此时间光线适合拍照，同时避免白天暴晒。

五、美食推荐真实化
当前：
12:00 品尝当地美食
没有价值。
要求：
必须推荐真实存在地点。
包括：
	•	餐厅名称
	•	推荐原因
	•	热门菜
	•	当地特色
例如：
不要：
“体验当地特色菜”
应该：
“XX餐厅”
推荐：
	•	普陀山特色素斋
	•	招牌菜
	•	游客常点菜

六、第二天/第三天行程完善
当前问题：
用户输入：
三天
但只生成两天。
这是严重问题。
要求：
严格按照用户旅行天数生成。
如果：
用户说三天：
必须输出：
Day1 Day2 Day3
不能缺失。

第三天返程逻辑
即使用户没有说返程时间，也需要合理推测。
例如：
第三天：
上午： 轻松安排附近体验
12:00： 午餐
13:30： 返程
理由：
避开下午高速拥堵。
或者：
晚餐后返程。

七、增加实时修改功能（重要）
当前：
虽然有：
	•	上一步
	•	修改选择
	•	返回首页
但是不符合真实使用场景。
要求：
在攻略详情页增加语音修改入口。
例如：
用户点击：
“调整攻略”
进入语音模式。
用户可以说：
“第三天我想吃完午饭再走”
系统：
理解 → 修改对应 Day3 → 更新攻略。
支持：
	•	修改时间
	•	增删景点
	•	修改同行人需求
	•	修改返程安排
这才符合 AI Agent 产品逻辑。

八、攻略分享展示优化
目标：
让用户可以直接给同行人看。
优化：
每个景点展示：
	•	去哪里
	•	几点去
	•	为什么去
	•	适合谁
例如：
“14:30 普济寺”
下面：
“下午游客较少，适合带父母慢慢参拜，不需要赶行程。”
让同行人一眼理解安排。

九、缓存问题
修改完成后：
必须确认清理旧缓存。
要求：
检查：
	•	Zustand 状态
	•	localStorage
	•	API 缓存
	•	页面缓存
	•	数据库旧数据
确保：
用户刷新页面后：
看到的是最新生成/修改后的攻略。
不要出现旧版本内容。

最终验收标准：
完成后测试：
输入：
“我和爸妈后天上海自驾去普陀山玩三天”
应该得到：
✅ 标题被重新总结 ✅ 三天完整行程 ✅ 所有选择卡片进入攻略 ✅ 每个时间点有真实地点 ✅ 餐厅真实推荐 ✅ 推荐菜存在 ✅ 父母出行节奏合理 ✅ 第三天有返程安排 ✅ 可以语音修改攻略 ✅ 刷新页面显示最新版本
请先分析涉及文件，再修改，不要只修改 UI 表面，需要同步调整 Prompt、数据结构和生成逻辑。
